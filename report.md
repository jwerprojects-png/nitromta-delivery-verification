# NitroMTA 0.2.1: one real TLS delivery from a fresh Linux runner

- **Result:** a genuine message reached the designated proof inbox at **2026-11-05T10:13:38.026Z**. NitroMTA emailed the operator a Nitrosend-published, address-free receipt: https://runx.ai/r/d95cf9be694d6b516955a654e62b2eb94f607947e3c2e3ea3bf4209101a0ddb3 . This receipt is external evidence; the local SMTP response alone was not used as proof.
- **Version and environment:** `nitromta 0.2.1`, x86_64, GitHub-hosted Ubuntu 24.04, Python 3.12.3. This was an ephemeral Linux runner controlled through my own GitHub repository, not a claim that NitroMTA ran on my Windows desktop. The run completed successfully: https://github.com/jwerprojects-png/nitromta-delivery-verification/actions/runs/42008903118 .
- **Installation:** downloaded the official `nitromta-0.2.1-x86_64-linux.tar.gz` release, verified it with `gh attestation verify nitromta.tar.gz --repo nitrosend/nitromta`, extracted it, and used its executable directly as the unprivileged runner user. No system service, paid cloud account or privileged installation was required.
- **Configuration changes:** ran `nitromta setup --config config.toml --capture`; removed exactly the `[capture]` table and replaced the documented `# port = 25` with `port = 2525` in `[delivery]`. All other generated settings were retained, including required delivery TLS. The private configuration contains generated installation keys and is intentionally not published.
- **Local identity and login:** ran `openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out dkim.pem`, then started `nitromta run --config config.toml`. Through `nitromta admin --config config.toml`, submitted `put_account` for account 1, `put_identity` for the reserved test domain `jwerprojects.example` with selector `qa` and the generated DKIM key, and `create_login` for user `qa`. The generated password was captured privately and masked, never placed in an artifact.
- **Send and validation:** Python's SMTP client connected to `127.0.0.1:2587`, performed STARTTLS using the generated `tls.crt` as its trusted certificate, authenticated with the generated login, and sent **one** plain-text message to the proof destination with the operator's controlled address in Reply-To. The subject was `Jwer Projects NitroMTA delivery check 2026-11-05T10:13:36.944304+00:00`. No TLS verification bypass was used. No other recipient or campaign was sent.
- **Observed engine evidence:** `nitromta_attempts_total{result="delivered"} 1`. `nitromta queue --config config.toml --json` returned `{"ok":{"queues":[],"stored":{"held":0,"in_flight":0,"waiting":0}}}`. The external proof email then independently confirmed arrival.
- **Expected warning:** the process log says DANE status could not be determined because the runner resolver returned a DNS server failure for the root keys. I retained the default TLS requirement and did not claim DNSSEC/DANE validation. This warning did not prevent the recorded delivery.
- **Timing:** the setup, key generation, launch, submission and confirmation by engine metrics took **3.88 seconds** in the recorded Python step. The official download/provenance step began at about 10:13:32 UTC; the external receipt records 10:13:38.026 UTC, approximately six seconds later. Preparing the reproducible remote workflow from Windows took several minutes before this measured run.
- **Slowest step:** arranging a Linux execution environment from a Windows machine without WSL, rather than installing or sending with NitroMTA itself. The archive avoided a source build and kept the test small.
- **Defects or documentation gaps:** none demonstrated in this one-message run. I checked the capture guide, installation guide, command-line reference and operations guide at release `v0.2.1`; exercised a fresh setup, generated login, signed identity, certificate-verified SMTP submission, actual delivery metrics and an empty final queue. This does not establish broad compatibility, sustained throughput or production deliverability.
- **Suggested improvement:** add a short, clearly labelled CI smoke-test example to the installation documentation that explains the transition from capture mode to a single consented test destination on a nonstandard delivery port. Keep the warning that this test does not validate production DNS or reputation, and show how to exclude generated keys and login responses from public artifacts.
- **Reproduction:** the exact executable workflow is https://github.com/jwerprojects-png/nitromta-delivery-verification/blob/126e5458eb97f3a16d16b3bc38a506d8bb455f97/.github/workflows/qa-delivery.yml . The run's `nitromta-verification-evidence` artifact contains the original automatically generated report and process log. Configuration, DKIM private key, login response and store were excluded. The temporary engine and its credentials ended with the runner.

No SPF, DMARC, reverse-DNS, production inbox placement or high-volume delivery claim is made. The test used the proof destination's documented permission to send with a reserved example-domain identity.
